# 오늘 점심 지도 기획서

Nov 1, 2026 · @수현

## 서비스 개요와 원칙

**한 줄 소개:** 오늘 점심 메뉴를 정하면, 그 선택이 모여 "오늘 우리 동네는 뭘 먹었나" 지도가 칠해지는 웹 서비스.

- **목적:** 포트폴리오로 완성하고, 스레드 공개 반응을 보고 운영 지속 여부를 정한다.
- **조건:** 1인 개발, 주 20시간 이상, 개발 기간 2\~3주.
- **핵심 루프:** 들어오면 동네 사람들이 오늘 많이 먹은 메뉴를 보고 → 메뉴를 고르면 근처 가게가 뜨고 → "이걸로 결정"을 누르면 그 선택이 지도에 한 표로 더해진다.
- **가칭:** 오늘 점심 지도 (이름 미정)

**원칙**

1. 회원가입과 로그인이 없다.
2. 서버에는 개인을 식별할 수 있는 정보를 남기지 않는다. 저장하는 것은 "날짜, 시군구, 메뉴 종류"별 표 수뿐이다.
3. 카카오에서 받은 가게 정보는 화면에 보여주기만 하고 저장하지 않는다.

**용어**

| 용어 | 뜻 |
| --- | --- |
| 메뉴 종류 | 투표 단위가 되는 고정된 분류 (한식, 국밥·탕, 면 등 10개) |
| 결정 | "이걸로 결정" 버튼을 누른 것. 1결정 = 1표 |
| 칸 | 지도에서 칠하는 단위 구역 (시군구) |
| 오늘 | 오전 5시부터 다음 날 오전 5시 전까지 (한국 시간) |

## 배경과 문제 정의

점심 메뉴 고민은 매일 같은 시간에 반복되는데, 지금 쓸 수 있는 도구는 내 주변 상황을 모른다.

- 메뉴 룰렛은 결정을 대신해 주지만, 근처에 그 메뉴 가게가 있는지는 따로 찾아야 한다.
- 지도 앱은 가게를 찾아 주지만, 메뉴를 정해 주지는 않는다.
- "남들은 오늘 뭐 먹었지"는 궁금하지만 볼 곳이 없다. 점심 메뉴 추천 콘텐츠가 꾸준히 만들어지는 것도 이 궁금증 때문이다.

이 서비스는 결정(룰렛) → 실행(근처 가게) → 공유(동네 점심 지도)를 한 화면 흐름으로 묶는다.

**핵심 가설**

- **H1.** 동네 사람들이 오늘 먹은 메뉴를 보여주면, 메뉴 결정이 빨라지고 재미를 느낀다.
- **H2.** 투표를 따로 요청하지 않고 메뉴 결정의 부산물로 만들면, 사람들이 "이걸로 결정"을 누른다.
- **H3.** 매일 바뀌는 점심 지도는 스레드에서 공유할 만한 콘텐츠가 되고, 그 공유가 다시 유입이 된다.

## 타깃과 페르소나

**주 타깃: 평일 점심 메뉴를 빨리 정해야 하는 20\~30대 직장인과 대학생.** "뭐 먹을지 고민하는 모든 사람"에서 평일 점심으로 좁혔다. 이유는 세 가지다.

1. **같은 시간에 몰린다.** 점심은 11시 반\~1시에 결정이 몰려서, 투표가 짧은 시간에 쌓이고 지도가 빨리 채워진다. 저녁은 시간대가 넓고 약속·배달·집밥이 섞여 표가 흩어진다.
2. **장소가 고정돼 있다.** 회사·학교 근처라는 같은 칸에서 매일 결정하므로, "우리 동네 오늘의 점심"이 의미를 가진다.
3. **고민이 매일 반복된다.** 매일 같은 시간에 돌아오는 고민이라 습관이 될 계기가 있다.

저녁·주말 사용자도 막지 않지만, 지도와 지표는 평일 점심 기준으로 설계한다.

**페르소나** (가상 인물, 가정)

|  | 김지훈 (31) | 박서연 (24) | 이민재 (28) |
| --- | --- | --- | --- |
| 상황 | 판교 IT 회사 직장인, 동료 2명과 점심 | 신촌 대학생, 주 3\~4회 혼밥 | 영업직, 주 2\~3회 낯선 동네로 외근 |
| 점심 고민 | 11시 40분마다 단톡방에서 "뭐 먹지"가 10분씩 오간다 | 매번 같은 메뉴만 먹어서 지겹다 | 처음 가는 동네라 어디서 먹을지 모른다 |
| 원하는 것 | 1분 안에 셋이 납득할 메뉴와 가까운 가게 | 새로운 메뉴 제안, 남들은 뭐 먹는지 구경 | 그 동네 사람들이 많이 먹는 메뉴와 근처 가게 |
| 쓰는 기능 | 룰렛 → 근처 가게 → 링크를 단톡방에 공유 | 동네 점심 지도 구경 → 메뉴 고르기 | 현재 위치 칸의 오늘 TOP 메뉴 → 근처 가게 |
| 다시 오게 하는 것 | 결정 시간이 줄어드는 경험 | 매일 바뀌는 지도 | 외근 갈 때마다 쓸 수 있는 도구 |

김지훈이 가장 중요한 페르소나다. 한 명이 쓰면 링크가 단톡방으로 퍼져서 여러 명이 들어오는 구조라 유입 효율이 가장 높다.

## 사용자 시나리오

**김지훈 · 평일 11시 40분, 판교 사무실**

1. 단톡방에서 "뭐 먹지"가 시작되자 사이트를 연다. 위치 권한을 허용하면 성남시 분당구가 잡힌다.
2. 첫 화면에 "오늘 분당구 점심 TOP 3: 국밥 · 면 · 한식"이 보인다.
3. 셋 다 당기지 않아 룰렛을 돌리고, "중식"이 나온다.
4. 근처 중식당이 거리순으로 뜬다. 첫 번째 가게 링크를 단톡방에 공유한다.
5. "이걸로 결정"을 누른다. 분당구의 중식 표가 하나 늘고, "오늘 분당구에서 중식 고른 사람 12명"이 뜬다. 여기까지 1분이 목표다.

**박서연 · 평일 12시 10분, 신촌 강의실**

1. 스레드에서 "오늘의 점심 지도" 캡처를 보고 링크로 들어온다.
2. 지도에서 서울 다른 구들은 뭘 먹었는지 구경한다. 강남구는 샐러드, 마포구는 면이 1위다.
3. 서대문구 TOP 메뉴인 "분식"을 눌러 근처 분식집을 보고 정한다.
4. "이걸로 결정"을 누른다. 내일도 지도가 어떻게 바뀌었는지 보러 올 이유가 생긴다.

**이민재 · 평일 12시, 처음 가는 대전 유성구**

1. 외근지에서 사이트를 연다. 대전 유성구가 잡힌다.
2. 유성구 오늘 표가 아직 적어서, 칸 대신 "대전 전체 오늘 TOP 3"가 보인다.
3. 1위인 "국밥"을 눌러 근처 국밥집 중 가장 가까운 곳으로 간다.
4. 시사점: 표가 적은 지역에서는 상위 행정구역으로 넘겨 보여줘야 빈 화면을 피할 수 있다.

**포지셔닝:** 룰렛의 가벼움에 "오늘 우리 동네 사람들의 선택"이라는 사회적 신호를 더한다. 개인 기록도 리뷰도 없고, 오늘의 점심만 다룬다.

**모방 가능성:** 기능 자체는 쉽게 따라 할 수 있다. 차별점은 쌓인 투표 데이터와 매일 올리는 "오늘의 점심 지도" 콘텐츠다. 포트폴리오 관점에서는 익명 집계 설계와 지도 시각화가 보여줄 지점이다.

## MVP 우선순위

MVP의 기준은 "오늘 동네 TOP 메뉴를 보고 → 고르고 → 근처 가게를 찾고 → 결정한다"는 한 바퀴와, 그것을 확인할 익명 계측이다.

| 우선순위 | 기능 | 이유 |
| --- | --- | --- |
| Must | 내 칸 찾기: 위치 권한 허용 시 자동, 거부 시 시군구 직접 선택 | 모든 화면의 기준. 권한을 거부해도 쓸 수 있어야 한다 |
| Must | 오늘 내 칸 TOP 3 메뉴 (표가 적으면 시도 → 전국으로 넘겨 표시) | H1. 첫 화면의 이유 |
| Must | 메뉴 종류 10개 선택 + 룰렛 | 결정 수단. 룰렛은 가볍게 구현 가능 |
| Must | 근처 가게 목록 (메뉴별, 거리순) + 카카오맵 상세 링크 | 결정을 실행으로 연결. 실시간 호출, 저장 없음 |
| Must | "이걸로 결정" = 1표 (기기당 하루 1회) | H2. 지도 데이터의 원천 |
| Must | 오늘의 점심 지도: 칸마다 1위 메뉴 색 | H3. 공유 콘텐츠의 원천 |
| Must | 남용 방지 기본 장치 | 로그인이 없어 도배에 취약하다 |
| Must | 익명 계측과 개인정보 안내 페이지 | 지표 확인, 무엇을 저장하지 않는지 알리기 |
| Should | 결정 직후 "오늘 분당구에서 중식 고른 사람 12명" | 결정에 대한 즉각 보상 |
| Should | 가게·결과 공유 링크 (단톡방용) | 김지훈 페르소나의 핵심 행동, 유입 경로 |
| Should | 지도 이미지 저장 | 스레드 연재용. 초기에는 직접 캡처로 대신할 수 있다 |
| Could | 오늘 결정 바꾸기 | 이전 표를 빼려면 표 식별이 필요해 구조가 복잡해진다 |
| Could | 어제·지난주 지도, 저녁 모드, 날씨 기반 추천 | 한 바퀴와 무관 |
| 제외 | 회원가입·로그인, 개인 기록, 리뷰·별점, 가게 즐겨찾기 | 원칙 1·2 |

**범위 점검:** Must 8개를 2\~3주 (주 20시간 기준 40\~60시간) 안에 끝내는 것이 목표다. 넘치면 남용 방지를 가장 단순한 형태로 줄이고, Should는 출시 후로 미룬다.

## 지도 표현 규칙

칸의 색은 오늘 그 칸에서 1위인 메뉴 종류이고, 표가 일정 수 미만인 칸은 칠하지 않는다. 빈 칸 대신 상위 지역의 결과를 보여줘서 빈 화면을 피한다.

**메뉴 종류 (10개)**

| 메뉴 종류 | 포함하는 메뉴 예시 | 가게 검색 키워드 |
| --- | --- | --- |
| 한식 | 백반, 찌개, 비빔밥 | 한식, 백반 |
| 국밥·탕 | 국밥, 설렁탕, 해장국 | 국밥, 해장국 |
| 면 | 국수, 칼국수, 냉면, 라멘 | 국수, 칼국수, 라멘 |
| 중식 | 짜장면, 짬뽕, 마라탕 | 중식, 중국집 |
| 일식 | 돈가스, 초밥, 덮밥 | 돈가스, 초밥, 덮밥 |
| 양식 | 파스타, 버거, 피자 | 파스타, 햄버거 |
| 분식 | 떡볶이, 김밥 | 분식, 김밥 |
| 고기·구이 | 제육, 불고기, 구이 정식 | 고기집, 제육 |
| 샐러드·건강식 | 샐러드, 포케 | 샐러드, 포케 |
| 아시안 | 쌀국수, 커리, 팟타이 | 쌀국수, 커리 |

**칠하는 규칙 (기준값은 가정)**

- **표시 기준:** 칸에 오늘 표가 5표 이상일 때만 칠한다. 가정: 1\~2표로 "오늘의 1위"를 정하면 한 사람의 선택이 칸 전체를 대표하게 된다.
- **넘겨 보여주기:** 내 칸이 5표 미만이면 시도 TOP 3를, 시도도 5표 미만이면 전국 TOP 3를 보여준다.
- **색:** 메뉴 종류마다 고정 색을 두고, 표 수에 따라 진하기를 3단계(5\~9표, 10\~29표, 30표 이상)로 나눈다. 10가지 색은 구분이 어려우므로 범례를 항상 띄우고, 칸을 누르면 TOP 3가 뜬다.
- **동률:** 1위가 동률이면 공동 1위로 표시하고 회색 빗금으로 칠한다.
- **하루의 경계:** 매일 오전 5시(한국 시간)에 새 지도로 바뀐다. 전날 지도는 보관만 하고 MVP에서는 보여주지 않는다.
- **칸 단위:** 시군구. 일반구가 있는 시를 나눌지와 2026년 7월 행정구역 개편 반영은 열린 질문으로 둔다.

## 개인정보를 남기지 않는 설계

서버로 보내는 것은 "날짜, 칸 코드, 메뉴 종류", 그리고 방문 경과·결정 소요 시간의 구간뿐이고, 위치 좌표와 기기 식별값은 브라우저 밖으로 나가지 않는다.

| 데이터 | 어디에 있나 | 서버로 보내나 |
| --- | --- | --- |
| 현재 위치 좌표 | 브라우저에서 칸을 판정하는 순간에만 사용 | 보내지 않음 |
| 칸 코드 (시군구) | 투표에 포함 | 보냄 |
| 메뉴 종류 | 투표에 포함 | 보냄 |
| "오늘 이미 결정함" 표시 | 브라우저 저장소 | 보내지 않음 |
| 처음 방문한 날 | 브라우저 저장소 | 날짜 대신 구간만 보냄 (첫날 / 2\~7일 / 8일 이후) |
| IP 주소 | 요청 처리 중에만 사용 | 저장하지 않음 (아래 남용 방지 참고) |
| 가게 정보 | 카카오에서 실시간으로 받아 화면에만 표시 | 보내지 않음, 저장하지 않음 |

**남용 방지 (3단계)**

1. **브라우저:** 하루 1회만 결정 버튼이 눌린다. 저장소를 지우면 우회되지만, 대부분의 사용자에게는 충분하다.
2. **서버:** 같은 IP에서 짧은 시간에 들어오는 요청을 제한한다. IP는 메모리나 만료되는 카운터에서만 쓰고 DB에 남기지 않는다.
3. **집계:** 한 칸에 1시간 동안 평소보다 크게 많은 표가 몰리면 그 표를 지도에서 보류하고 수동으로 확인한다. 기준값은 운영 데이터를 보고 정한다.

**재방문을 재는 방법:** 기기 식별값 없이, 투표에 "처음 방문 후 경과 구간"만 붙인다. 그러면 "오늘 표 중 8일 이후 다시 온 사람의 비율"을 사람을 식별하지 않고 볼 수 있다.

**확인할 것:** IP·브라우저 저장소 사용이 법적으로 어디까지 개인정보 처리에 해당하는지, 좌표를 서버로 보내지 않을 때 위치정보법상 신고가 필요한지는 미확인이다. 출시 전에 확인하고, 안내 페이지에 "무엇을 저장하지 않는지"를 그대로 적는다.

## 화면 구성

화면은 홈 하나와 그 위에 올라오는 시트들로 구성한다. 페이지 이동 없이 한 손으로 1분 안에 끝나는 흐름이 목표다.

1. **홈:** 상단에 내 칸 이름과 "오늘 TOP 3" 메뉴 칩, 가운데 메뉴 종류 10개와 룰렛 버튼, 하단에 "오늘의 점심 지도 보기".
2. **가게 시트:** 메뉴를 고르면 아래에서 올라온다. 근처 가게가 거리순으로 보이고, 가게를 누르면 카카오맵 상세로 이동한다. 맨 아래에 "이걸로 결정" 버튼.
3. **결정 완료:** "오늘 분당구에서 중식 고른 사람 12명"과 공유 버튼 (Should).
4. **오늘의 점심 지도:** 전국 칸 색칠 지도, 범례, 칸을 누르면 그 칸의 TOP 3.
5. **내 칸 바꾸기:** 위치 권한이 없거나 다른 동네를 보고 싶을 때 시도 → 시군구를 고른다.
6. **안내:** 무엇을 저장하고 무엇을 저장하지 않는지, 문의처.

## 기술 스택과 데이터 구조

이전 기획보다 서버 역할이 크게 줄어, 서버는 "표를 더하고 집계를 돌려주는" 일만 한다. 가게 검색과 칸 판정은 브라우저에서 끝낸다.

| 영역 | 선택 | 용도 |
| --- | --- | --- |
| 프론트엔드 | Next.js (App Router) + TypeScript, Vercel 배포 | 화면, 투표·집계 API (Route Handler) |
| 가게 검색 | 카카오맵 JavaScript SDK의 services 라이브러리 | 메뉴 키워드 + 현재 좌표로 근처 가게 검색. JS 키는 등록 도메인에서만 동작 |
| 칸 판정 | 같은 SDK의 좌표 → 행정구역 변환 | 좌표를 시군구 코드로 바꾼 뒤 좌표는 버린다 |
| 점심 지도 | 단순화한 시군구 경계 GeoJSON + SVG (d3-geo) | 전국 지도를 가볍게 그리고 캡처하기 쉽게. 카카오 지도 타일은 쓰지 않는다 |
| 저장소 | Supabase Postgres (로그인 기능은 쓰지 않음) | 표 수와 이벤트 수만 저장 |
| 남용 방지 | 만료되는 카운터 (예: Redis 계열 서비스) | IP별 요청 수 제한, IP는 DB에 남기지 않음. 도구는 결정 필요 |

**데이터 구조 (초안)**

- `vote_counts`: vote\_date, region\_code, menu\_type, visit\_bucket, count. 앞의 네 열이 기본 키이고, 투표가 오면 해당 행의 count를 1 올린다.
- `event_counts`: event\_date, name, count. 홈 진입, 메뉴 선택, 결정 같은 단계별 횟수만 센다.
- 시군구 목록(코드, 이름, 시도)과 경계 파일은 레포에 정적 파일로 둔다.
- 쓰기는 Route Handler에서 서버 전용 키로만 하고, 브라우저에서 DB에 직접 쓰지 못하게 막는다.

**API**

| 경로 | 하는 일 | 캐시 |
| --- | --- | --- |
| POST /api/vote | 칸 코드·메뉴 종류·방문 구간을 받아 표 1개 추가 | 없음 |
| GET /api/today?region= | 칸 TOP 3 (표가 적으면 시도·전국으로 넘김) | 30\~60초 (가정) |
| GET /api/map | 오늘 칸별 1위 메뉴와 표 수 | 30\~60초 (가정) |

카카오 JS SDK의 결과 수 한도(한 번에 최대 45개, 반경 최대 20km)는 개발자 블로그로 확인한 값이라, 개발 시작 전에 공식 문서로 다시 확인한다.

## 성공 지표와 검증 계획

개발과 함께 1주 동안 스레드에서 수요를 먼저 확인하고, 출시 후 4주 동안 아래 지표로 운영 지속 여부를 정한다. 목표치는 모두 가정이다.

**사전 검증 (개발 1주차와 병행)**

평일 5일 동안 11시쯤 스레드에 "오늘 점심 뭐 드셨어요? 동네랑 메뉴 댓글로"를 올리고, 다음 날 댓글을 모아 손으로 만든 지도를 공유한다.

- **진행 기준:** 평일 하루 평균 댓글 10개 이상 (가정: 서비스 출시 후 첫 칸을 칠할 5표를 모을 수 있는 최소 반응).
- **미달 시:** 개발은 포트폴리오 목적으로 계속하되, 홍보 채널과 첫 화면 메시지를 다시 정한다.

**출시 후 지표**

| 가설 | 지표 | 목표치 (가정) | 가정의 근거 | 측정 방법 |
| --- | --- | --- | --- | --- |
| H1 | 홈 진입 → 결정까지 걸린 시간 중앙값 | 60초 이하 | 점심 대화가 오가는 짧은 시간 안에 끝나야 쓸모가 있다 | 브라우저에서 구간(30초 미만/30\~60초/60초 이상)만 계산해 전송 |
| H2 | 결정 전환율: 홈 진입 대비 결정 수 | 30% 이상 | 구경만 하는 방문도 많을 것으로 보고 보수적으로 잡았다 | event\_counts |
| H2 | 평일 하루 결정 수 | 출시 2주 뒤 평균 50표 이상 | 5표 이상 칸이 몇 개는 생겨야 지도가 지도처럼 보인다 | vote\_counts |
| H3 | 오늘 표 중 처음 방문 후 8일 이후 구간의 비율 | 30% 이상 | 매일 다시 오는 사람이 있어야 지도가 쌓인다 | visit\_bucket 집계 |
| H3 | 스레드 게시물 유입 수, 공유 버튼 클릭 수 | 방향만 확인 | 표본이 작아 크기보다 추세를 본다 | 유입 태그가 붙은 링크, event\_counts |

**운영 지속 기준 (출시 4주 뒤):** 평일 평균 결정 50표 이상이고 8일 이후 재방문 비율 30% 이상이면 계속 운영한다. 아니면 포트폴리오로 마감하고, 지표와 회고를 정리한다.

## 로드맵

개발 3주 (마지막 주 절반은 버퍼) 뒤에 출시하고, 4주 동안 운영 지표를 본다. 주 20시간 기준이며, 각 주는 완료 조건을 채워야 끝난다.

1. **1주차 — 결정 흐름 (사전 검증 병행)**
   - 카카오 쿼터·활성화 이력 확인, 시군구 경계와 카카오 행정구역 코드 매칭 확인
   - 내 칸 찾기(위치·직접 선택), 메뉴 10개와 룰렛, 근처 가게 시트
   - 스레드 사전 검증 5일 진행
   - **완료 조건:** 실제 휴대폰에서 메뉴를 고르면 근처 가게가 1초 안팎으로 뜬다 (가정). 경계 근처 테스트 좌표 20개가 맞는 칸으로 판정된다. 사전 검증 결과가 기록돼 있다.
2. **2주차 — 투표와 지도**
   - 투표 API와 DB, 오늘 TOP 3와 상위 지역으로 넘기기, 오늘의 점심 지도(SVG), 남용 방지 1·2단계
   - **완료 조건:** 테스트 투표 100개를 넣으면 지도와 TOP 3가 규칙대로 칠해진다. 같은 기기에서 두 번째 결정이 막힌다. DB에 좌표와 IP가 없다.
3. **3주차 — 출시 준비와 출시**
   - 익명 계측, 안내 페이지, 모바일 화면 다듬기, 남용 방지 3단계 수동 확인 절차
   - 시간이 남으면 Should (결정 직후 메시지, 공유 링크)
   - **완료 조건:** 지표 표의 모든 항목이 집계된다. 스레드에 출시 글을 올렸다.
4. **출시 후 4주 — 운영 검증**
   - 평일 11시 전후 "오늘의 점심 지도" 연재, 주 1회 지표 확인
   - **완료 조건:** 운영 지속 기준에 따라 계속 운영할지, 포트폴리오로 마감할지 결정했다.
